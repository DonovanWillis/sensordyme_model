SensorDyme — Complete System Architecture & Technical Audit

Audit date: Monday 9 November 2026 · Repository: ~/Sensordyme/sensordyme_model (origin DonovanWillis/sensordyme_model, branch integration/all @ a779b4d) · Method: static inspection plus live tests against the running Mac backend, the Raspberry Pi over SSH and LAN, local Ollama, and Xcode 27.2.

1Executive summary

SensorDyme is an edge computer-vision monitoring product with four main parts:

  • a Raspberry Pi 5 with a Camera Module 3 NoIR Wide and a Hailo-8L AI HAT+, running a Python detection runtime;
  • a FastAPI + SQLite backend that currently runs on your Mac as a launchd service;
  • a SwiftUI iOS app;
  • an LLM layer called Jupiter, which turns plain-language monitoring requests into structured detection rules.

Everything lives in one repository, sensordyme_model. A separate folder, ~/Sensordyme-website, holds a static marketing site.

Why everything stopped working Shortly before this audit, the previous working checkout ~/sensordyme_model was moved to the macOS Trash, and a fresh clone was made at ~/Sensordyme/sensordyme_model. The backend's launchd job still pointed at the old path. The old checkout held every piece of runtime state that git deliberately does not track:
  • the SQLite database (accounts, devices, events);
  • the JWT signing secret;
  • the backend identity file;
  • the .venv;
  • data/;
  • the generated Xcode project.
The backend kept running from inside the Trash, but it could not open its database (every request returned HTTP 500 or 503). It also reported a new, freshly generated backend id (bk_6251e874…), so the iPhone app, which pins the original id bk_0eb63f4fc338, would refuse to use it. The Pi's cloud uplink was failing with HTTP 500 for the same reason.
Unpushed work found in the Trash, now backed up The trashed checkout is on branch rebuild/oryn-edge-app, which has 48 commits (20–22 Oct 2026, 96 files, about +6.8k lines) that exist nowhere else: not on GitHub and not in the new clone. They contain the "ORYN Edge" rebrand of the device and app. Separately, GitHub's integration/all has a newer commit a779b4d "sfxbx" (15 Oct, by a collaborator) that the old checkout never fetched. 3Software architecture

The system has three runtime tiers plus an LLM service. The device does all vision locally. Frames never leave the LAN, and only event metadata travels upstream. The backend is the account and control plane. The iPhone talks to the backend for accounts, events and configuration, and talks directly to the device on the LAN for live video.

Device process model

The device runs as one systemd service (sensordyme.service, Type=notify, with a watchdog) in one Python process with supervised threads:

  • Capture owns the camera.
  • Inference always processes the newest frame, never a backlog.
  • Dashboard, CloudUplink, Provisioning and HealthMonitor run alongside.

The heavy work (capture I/O, MediaPipe/ONNX, Hailo calls, JPEG encode) releases the GIL. Recovery escalates in this order (ARCHITECTURE.md):

  1. in-place camera re-open
  2. component restart
  3. service-thread restart
  4. the watchdog lets systemd restart the process
  5. rate-limited reboot

Profiles and presets

config.yaml: profile: pi is the shipping product. mac_max is a Mac-only demo and accuracy-ceiling profile: YOLO11x on Apple MPS plus a VLM judge.

presets.yaml maps product modes to modules:

A fifth runtime mode, AI_CUSTOM, runs Jupiter-generated rules on top of occupancy, or fall_detection when every rule is pose-only.

4Web application architecture

There is no separate SPA or web framework. SensorDyme's "web application" consists of two parts:
  1. the on-device dashboard: inline HTML/CSS/JS served by Python's stdlib ThreadingHTTPServer in core/dashboard.py;
  2. the backend REST API, which only the iOS app uses (there is no web client for it).
site/index.html and ~/Sensordyme-website/sensordynewebsite (about, product, solutions, technology pages, with a CNAME) are static marketing sites with no API calls.

Device dashboard (core/dashboard.py, port 8899)

  • Frontend. A single inline page (_PAGE) with five parts:
    • live video panel with an alert pill and a red flash overlay on each new event;
    • risk sparkline drawn on a canvas;
    • mode chips for switching presets;
    • session stats;
    • alert timeline.
    It polls /api/state every 400 ms and /api/presets every 5 s. All inserted text is escaped. A second page, _SETUP_PAGE, is a Wi-Fi form used by the legacy hotspot onboarding flow.
  • Auth. Every /api/* and /stream request, and every POST, needs X-Device-Token (or ?token= for the <img> MJPEG case), compared in constant time. If no token is configured on a non-loopback bind, it fails closed. The shipped config.yaml has token: null; your Pi has a token set.
  • Account management. None at the device level. Accounts live in the backend.

5Backend architecture

Stack

  • FastAPI 0.141, Starlette 1.4 and uvicorn, in one module cloud/app.py (about 2.8k lines).
  • SQLite in WAL mode with a 15 s busy timeout. Files are set to 0600.
  • Migrations are additive: CREATE TABLE IF NOT EXISTS plus a list of ALTER TABLE ADD COLUMN. There is no version table. This is why the older database opened cleanly under the new code.
  • Request bodies are capped at 4 MB.
  • sqlite3.OperationalError is mapped to 503, so devices retry instead of dropping events.
  • Retention: 90 days or 100k events per device, applied at most hourly.

Deployment

Current: Mac LaunchAgent com.sensordyme.backend.

  • Runs uvicorn cloud.app:app --host 0.0.0.0 --port 8787.
  • Environment: SENSORDYME_MDNS=1.
  • Logs go to cloud/backend.log.

Alternative: Fly.io (fly.toml, app sensordyme-api, volume mounted at /data). It is configured but not in use, and CI does not deploy it.

Authentication

  • Users
    • Passwords are hashed with PBKDF2-HMAC-SHA256 (200k iterations, per-user salt). Unknown emails take the same time to fail.
    • Sessions are HS256 JWTs with a 30-day lifetime and a revocable jti.
  • Devices
    • Each device sends X-Device-Key (dk_…), created with cloud/manage.py create-device.
    • Users claim a device with a 12-hex claim code.
  • Rate limits (in memory)
    • login, signup and claim: 10 per 5 minutes per IP;
    • failed logins: 20 per 15 minutes per email;
    • AI: 30 per minute and 2 concurrent per account, 8 concurrent globally.

Notifications

There is no APNs. Background alerts are delivered to ntfy.sh topics. SMS goes through Twilio when the TWILIO_* environment variables are set; otherwise it is only logged. cloud/notify.py only lets an event through when both of these hold:

  • it is "loud" or comes from a custom_rule;
  • the account is outside its 20 s cooldown.

Frame-to-alert pipeline

Key mechanics

  • One surface for both backends. Modules call get_yolo_model(weights).predict(frame, classes=[…], conf=…). Hailo and ultralytics expose the same interface.
  • Hailo lifecycle.
    • Setup chain: VDevice → ConfigureParams.create_from_hef(PCIe) → network group → InferVStreams.
    • The network is activated once and held open; calls are serialised by a lock.
    • A device fault tears it down, and the next frame rebuilds it.
    • release_all() runs at shutdown.
  • Decoding the raw HEF.
    • Output shapes are paired into box and class heads.
    • Boxes use DFL over 17 bins.
    • Class scores are assumed to be already sigmoid'd.
    • Class-wise greedy NMS in numpy, IoU 0.50, hard-coded.
    • Class names always come from the hard-coded COCO_NAMES.
  • Confidence thresholds.
    • driver_attention: 0.20, with person filtered at 0.50
    • occupancy: 0.5
    • baby_monitoring: 0.4
    • mac_max: 0.4
  • Integrity.
    • The .hef sha256 is checked against the pin at every load (not every frame), and re-hashed after load.
    • On a mismatch the model is refused and the runtime goes DEGRADED.
    • The Pi has no CPU fallback, because ultralytics is deliberately not installed there.
  • Model identity. Each uplinked event carries model: {module, detector:{name, sha256, backend}}, which the backend stores in events.model. Your Pi's older code doesn't send it yet.
  • Updating the model. There is no OTA. Changing the model means re-running setup_pi.sh and editing the config, because make deploy deliberately excludes *.hef and config.yaml.

Live evidence

/api/health accelerator component reported: "Hailo NPU in use — 8577 inferences, last 0.11s ago" and "running on the Hailo-8 accelerator". A frame from /stream showed the full overlay: EAR, yaw, risk bar, "FACE NOT VISIBLE", and a YOLO box. That box was a false positive: a window blind labelled spoon. The unit was pointed at a desk rather than a driver, which also produced repeated eating_drinking and phone_detected log events.

Known CV defects (from code review)

  1. One exception in _update_object_detections permanently disables object detection in driver_attention and mac_max until restart, and health still reports monitoring as active (modules/driver_attention.py:1331–1359).
  2. Open anchor-offset question in the DFL decoder: the code places anchors at cell centre + 0.5 (accel.py:673–694). If upstream DAMO-YOLO differs, every box is shifted by stride/2. Nothing measures box position.
  3. setup_pi.sh accepts an older 4c71eab8… build that config.yaml forbids. Such a device installs and then boots DEGRADED. Most published accuracy numbers were measured on that older build.
  4. scripts/migrate_config.py never adds accelerator.yolo_hef or its sha pin. An old config becomes either DEGRADED or unpinned.
  5. NMS IoU and class names are hard-coded, so a custom-class model would silently use the wrong names.

8EVE / Jupiter intelligence architecture

Jupiter is a coordinator, not a vision model (jupiter/__init__.py). Vision never passes through the LLM. Jupiter has exactly two LLM roles:

configure

Turns a user's request ("tell me if someone holds a phone for 10 s") into a list of RuleDraft objects. Each rule has these fields:
  • target, predicate, secondary
  • zone, persist_s, min_count
  • confidence, severity, cooldown, schedule, notify
Every field is validated against the capability registry (core/capabilities.py).

explain

Rephrases a deterministic list of facts about one alert (signals, confidence, duration, zone, model) into at most 30 words. It is never used for CRITICAL events (falls, zone exits); those keep their deterministic text.

How detections become decisions

  • Built-in presets. Each module fuses YOLO boxes with MediaPipe signals into per-frame booleans. EventEngine confirms them using persistence, a minimum frame count, occlusion grace and cooldown, then assigns a severity tier (loud, soft or log).
  • AI_CUSTOM. The RuleEngine checks each rule against the raw DetectionFrame (COCO label, confidence, box) on every frame. It applies schedule windows, binds rules to zones (an undrawn zone makes the rule inert, never frame-wide), and enforces floors: persist ≥ 0.5 s, ≥ 2 frames, cooldown ≥ 5 s.
  • Human in the loop. A Jupiter proposal is only ever stored as a draft. The user has to press Activate in the app before the device receives it.

Context, memory and history

None is implemented. Each interpret() call is stateless: one system prompt plus one user message (docs/JUPITER.md: "no memory across requests"). Only the following persist:

  • the rules themselves, with the original instruction;
  • the events table, which explain reads one event at a time, deterministically;
  • the VLM judge's in-memory streak.

core/reports.py builds a weekly PDF from events.csv with no LLM involved, and only tests call it. core/activity.py does deterministic pose-based activity classification.

How YOLO and an LLM should divide the work

Computer vision (YOLO + MediaPipe): perception

  • Runs every frame, in milliseconds, on the device, deterministically.
  • Answers "what objects or poses are where, with what score".
  • Handles all safety-critical, time-critical alerting (drowsiness, falls, zone exits).
  • Does not need connectivity and never sends frames off the device.

LLM (Jupiter): intent and language

  • Before runtime, it compiles what the user wants into checkable rules (already built).
  • After an event, it explains the alert in plain words (already built).
  • Possible future uses:
    • summarise event history ("unusual activity this week");
    • suggest rule adjustments from false-alarm feedback;
    • triage ambiguous events, optionally with a VLM looking at a single frame on demand.
  • Never in the per-frame loop, and never the only gate on a safety alert.

The architecture already follows this split. The natural extensions are listed in §18.

App structure

  • SensorDymeApp → RootView:
    • signed out → AuthView: sign in, sign up, or "Try the demo" (a full MockAPI);
    • signed in → tabs Devices / Shop / Settings.
  • Shared state lives in one @MainActor AppState (API.swift): backend addresses and pinned id, Keychain tokens, device link, connection status, a 20 s heartbeat, and an NWPathMonitor that triggers a reconnect when the network changes.
  • DeviceDetailView:
    • live MJPEG feed;
    • mode switcher;
    • event list (polled every 4 s), with event details;
    • an "explain" view per event;
    • AI Configure (prompt → editable proposal → Activate);
    • zone editor (normalised polygons);
    • Reports (Swift Charts);
    • rename.
  • Settings: server address (automatic or manual), device link with "Find my device", device token, device health card, SMS, ntfy background alerts, a 6-stage connection doctor (DiagnosticsView), and BLE setup.
  • Finding the backend.
    • Precedence: typed URL > build-time SENSORDYME_API_BASE_URL (empty) > Bonjour _sensordyme-api._tcp.
    • Every candidate is health-checked: it must answer service=="sensordyme-cloud" with the pinned id.
  • Finding the device.
    • Bonjour _sensordyme._tcp, matched by its TXT id=SD-….
    • The live feed is shown only when the SD- id matches the backend device's hardware_id (FeedLink.swift).
  • Notifications.
    • Local notifications only, posted by AlertWatcher, which polls every 15 s in the foreground.
    • Background alerts go through ntfy or SMS.
    • APNs is listed as future work.
  • BLE provisioning.
    • Service 5d1e0001-5344-4d45-b000-536e447a6d65.
    • Characteristics: info …0002, creds …0003, status …0004, networks …0006.

Recovery steps performed

  1. xcodegen generate → ios/SensorDyme.xcodeproj (scheme SensorDyme).
  2. xcodebuild -scheme SensorDyme -destination id=<your iPhone> -allowProvisioningUpdates build. Xcode chose the "iOS Team Provisioning Profile: com.sensordyme.app" and your Apple Development identity. Swift compilation: 0 errors, 0 source warnings.
  3. Code signing stopped at a macOS Keychain access prompt for the signing key (SecurityAgent). That needs your password and a click on Always Allow. It cannot be automated.
  4. Final state: the command-line build ended ** BUILD FAILED ** at CodeSign with errSecInternalComponent, because the Keychain prompt was never approved. Signing from a non-interactive shell needs that one-time approval. Everything before signing succeeded.

Code-quality notes (not blocking)

  • APIClient.getJSON/postJSON skip the "find the server again and retry" logic and the error mapping used by request(). This affects AI configure, zones, explain, rename, orders and logout, which handle a backend move less gracefully than the other calls.
  • "Add device" still opens the legacy hotspot wizard. ClaimDeviceView, ensureBackend() and stopBackendMonitoring() are unused.
  • Deprecations: NetService and .cornerRadius. Several Swift 6 strict-concurrency issues would appear if the language mode were raised.

Offline behaviour

  • The device keeps detecting, alerting locally and serving its dashboard with no network.
  • Uplink events queue in memory: at most 500, newest kept, lost on restart.
  • The backend deduplicates resent events on (device_id, event_key).
  • This was confirmed during the audit: after the backend was restored, the Pi's queued backlog arrived in one burst at 21:04:18.

Privacy boundary

Frames never leave the device and are never uploaded. Only event metadata goes to the backend. The single exception is the mac_max VLM judge, which sends JPEGs to an external API, and it runs only on a Mac.

  • On-device driver monitoring:

    • phone use;

  • Offline-tolerant uplink to a FastAPI backend with accounts, device claiming, event history, zones, ntfy push and SMS.

  • iOS app: login, devices, live feed, events, AI configure, zones, reports, BLE setup, diagnostics, local notifications, demo mode.
  • Test infrastructure: 128 pytest files, Swift logic tests, CI with lint, typecheck, audit and mutation testing.

16Incomplete or broken functionality

  • EVE does not exist in the codebase under that name. The equivalent layer is Jupiter. History and memory-aware reasoning are not implemented.
  • APNs push is not implemented. Notifications are local while the app is in the foreground, plus ntfy and SMS.
  • Remote access is missing: no Tailscale, and Fly.io is configured but unused. Away from the LAN, the phone cannot reach the Mac backend or the Pi.
  • Over-the-air model and code updates are missing. Updates need make deploy and setup_pi.sh by hand.
  • Pi software is stale compared with the repo (§6).
  • Jupiter's cloud fallback is off, and the anthropic package is not in the backend requirements.
  • Pose-based capabilities on the backend: mediapipe is not in cloud/requirements.txt, so a Fly-deployed backend would treat resting, waving and lying down as unavailable. The Mac venv does now have MediaPipe.
  • Declared but unavailable: identity tracking, action recognition, fire/smoke, packages, eyewear.
  • Diverged history: the ORYN Edge rebrand branch is not merged or pushed.

Readiness summary The repo is strong on inference, integrity and measurement. It pins the model, records model identity, and has a regression gate. It is weak on everything upstream of a .hef: there is no detection labelling, no YOLO-format export, no training code, and no DFC compile step. The quickest credible path:
  1. Self-host Label Studio with a bounding-box template, plus an ML backend that pre-labels with the current DAMO-YOLO.
  2. Export to YOLO or COCO.
  3. Fine-tune DAMO-YOLO-T (Apache-2.0, the same architecture as the shipped model) on a GPU.
  4. Compile with the Hailo DFC on x86 Linux, using about 64–1024 calibration frames from the real NoIR camera.
  5. Evaluate with the existing benchmark gate, extended with mAP.
  6. Pin the sha256 and deploy.
Two code changes are prerequisites: custom class names, and a configurable class count and NMS IoU in core/accel.py. Stay off ultralytics for anything that ships (AGPL).
